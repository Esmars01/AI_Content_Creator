# Deployment

How to run the Creator Engine beyond a developer laptop: the supported topologies, what production
requires, and a checklist. Day-two operations (alerts, backups, upgrades) are in
[`OPERATIONS.md`](OPERATIONS.md); hardening in [`SECURITY.md`](SECURITY.md).

**Status.** No production deployment exists. What has been run is the mock-mode stack on one host: Docker
Compose infrastructure with the services either as Compose containers (earlier phases) or as host processes
(`make dev-native`, Phase 14, on a host that cannot build the service images), plus the observability
profile. **Production cannot start today**: it requires real, production-validated watermark adapters (I11),
and the VideoSeal/AudioSeal adapters are `untested_on_gpu`; every GPU engine is untested on a GPU
([`GPU_VALIDATION.md`](GPU_VALIDATION.md)). Kubernetes manifests are not provided (`infra/k8s/` is a
placeholder).

## Topologies

### 1. One host, Compose (development, demos, small trials)

```bash
cp .env.example .env        # dev-only credentials
make dev                    # infrastructure + migrations + seed + api, web, orchestrator, scheduler, render worker, worker-cpu
make obs-up                 # optional: Prometheus, Alertmanager, Grafana, Loki, Tempo, OTel collector
```

Service images are built from `infra/docker/` (`make build-images`; `EXTRA_CA_BUNDLE=<path>` behind a
TLS-intercepting proxy). Everything runs in mock mode (`MOCK_GPU=true`, fixture LLM, `PROVENANCE_MODE`
resolving to `mock_dev`): renders are stamped "MOCK PROVENANCE — NOT FOR DISTRIBUTION" and cannot be exported.

### 2. One host, native services (when images cannot be built)

```bash
make infra-up               # Postgres+pgvector, Valkey, Temporal, SeaweedFS in containers
make dev-native             # migrations, seed, then the services as host processes (scripts/dev_native.py)
make obs-native             # optional observability, scraping the host processes
make dev-native-down
```

Needs the toolchain of [`SETUP.md`](SETUP.md) (uv, Python 3.12, Node + pnpm, FFmpeg). Logs go to
`.data/native/<service>.log`; ports are listed in [`OBSERVABILITY.md`](OBSERVABILITY.md). This is how Phase 14
was verified.

### 3. Split: control plane + GPU workers

The control plane (web, API, orchestrator, render workers, scheduler, Postgres, Valkey, Temporal, object
store) runs on CPU hosts; GPU workers run wherever GPUs are and need only:

- HTTPS reach to the scheduler's worker API (`SCHEDULER_PUBLIC_URL`) — workers lease work, heartbeat and
  upload outputs through presigned URLs, so they need no database or Temporal access;
- reach to the object store's public endpoint (`S3_PUBLIC_ENDPOINT_URL`) for presigned downloads and uploads;
- a registration secret: `WORKER_TOKEN` (≥ 32 characters in production) or a one-time enrollment token
  issued by the fleet manager or `POST /v1/admin/gpu/workers:enroll`;
- the model cache (`MODEL_CACHE_DIR`), filled from pinned, checksum-verified sources.

Worker images per runtime family are generated by `scripts/gen_worker_dockerfiles.py`
(`infra/docker/worker-*.Dockerfile`). The fleet manager can provision workers on configured GPU providers
(`gpu_providers` rows; drivers exist for RunPod, a local Docker host and a mock, plus an example cloud driver) — **never enable a paid provider without the product
owner's explicit approval**: provisioning spends money, capped by `BUDGET_DAILY_USD` and per-video and
per-project budgets ([`GPU_SETUP.md`](GPU_SETUP.md)).

### Scaling

| Component | Scales | Notes |
| --- | --- | --- |
| web, API | horizontally, stateless | put them behind the TLS proxy; sessions live in Postgres |
| orchestrator, render workers | horizontally (Temporal task queues) | render workers are CPU- and disk-bound (FFmpeg) |
| scheduler | horizontally; one leader (Postgres advisory lock) runs the reaper, fleet and metrics loops | every replica serves the worker API |
| GPU workers | by the fleet manager per pool, or by hand | see [`LOAD_TEST.md`](LOAD_TEST.md) for the measured scheduler limits on one host |
| Postgres | vertically; read replicas are not used | the queue (`gpu_tasks`) uses `SKIP LOCKED` leasing |
| object store | any S3-compatible store | SeaweedFS in development |

## Production requirements

Set `APP_ENV=prod`. The services then refuse to start (`ce config validate --env prod --startup` lists every
refusal without starting anything) unless:

- `SECRET_KEY` is at least 32 characters and not a dev value; `WORKER_TOKEN` likewise;
- `COOKIE_SECURE=true` (the default in `config/env/prod.yaml`);
- provenance is `real` and, for each provenance capability (C2PA signing, video and audio watermarks), a
  non-mock adapter is production-routable (status `production`, smoke- or bench-validated, not disabled);
  C2PA needs operator certificates (`C2PA_SIGNING_CERT_PATH`, `C2PA_SIGNING_KEY_PATH`);
- production routing uses only adapters with `smoke_passed` or `bench_passed` and a license closure that
  permits the operator's profile (`OPERATOR_JURISDICTION`, `OPERATOR_REVENUE_BAND`).

Also required, though not checked at startup:

- a TLS-terminating reverse proxy in front of the web app that **overwrites** `X-Forwarded-For` with the peer
  address; `FORWARDED_ALLOW_IPS` on the API set to the web gateway's address; `WEB_HSTS=true` at web build
  time ([`SECURITY.md`](SECURITY.md#deploying-safely));
- the API, metrics (9100) and infrastructure ports not published; only the web app and the scheduler's worker
  API (TLS) reachable from outside;
- managed or replicated Postgres with point-in-time recovery, an object store with versioning, and the backup
  drill in [`OPERATIONS.md`](OPERATIONS.md#backup-and-restore) run regularly;
- an LLM provider configured (`LLM_PROVIDER`, `LLM_MODEL`, its key) if the Director should not run on
  fixtures, and an `embed.text` model once one is pinned and license-verified (none is registered today);
- verified platform rules (`config/platforms/*.yaml`, `verified_at`, `sources`) before packaging limits are
  presented as platform facts;
- an Alertmanager receiver, and the alert thresholds reviewed for your traffic.

An example proxy block (nginx):

```nginx
server {
  listen 443 ssl http2;
  server_name studio.example.com;
  # ssl_certificate …; ssl_certificate_key …;
  client_max_body_size 64m;              # uploads go to the object store directly; this covers API bodies
  location / {
    proxy_pass http://web:3000;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $remote_addr;   # overwrite, never append the client's value
    proxy_set_header X-Forwarded-Proto https;
    proxy_buffering off;                 # server-sent events
    proxy_read_timeout 1h;
  }
}
```

## Checklist

1. Infrastructure: Postgres 18 with pgvector, Valkey/Redis, Temporal, an S3-compatible store with two buckets.
2. `.env` from `.env.example` with production values; `ce config validate --env prod --startup` clean.
3. `make migrate`, `ce storage init`; create the first org and admin (`ce seed` is for development only).
4. Services started; `/readyz` green; Prometheus targets up; a test plan → previz → build in a test project.
5. Backups scheduled and one restore drill done; alerts routed.
6. GPU workers registered (`GET /v1/gpu/workers`) and their adapters smoke- and bench-validated on the target
   GPU class before production routing uses them.
